# 질문 흐름 (question-flow)

위저드의 각 Step에서 던질 질문문·선택지·분기 규칙을 모았다. SKILL.md의 워크플로우를 진행하며 이 문서를 따른다. 모든 질문은 `AskUserQuestion` 다지선다이며, 무난한 선택지를 첫 번째에 두고 라벨 끝에 "(추천)"을 붙인다.

## 목차
1. 프로젝트 감지 규칙
2. Step 0 — 기존 설정 보완 방식
3. Step 2 — 깊이 선택
4. 깊이별 분기 매트릭스
5. Step 3 — 핵심 설정 질문들
6. Step 4 — 스타터(확장)
7. Step 5 — 미리보기 확인

---

## 1. 프로젝트 감지 규칙

사용자에게 묻기 전에 루트의 신호 파일을 읽어 추론한다. 추론값은 **기본 제안**일 뿐, Step 1에서 반드시 확인받는다.

| 신호 파일 | 추론 | 명령 추출 위치 |
|-----------|------|----------------|
| `package.json` | Node/JS·TS | `scripts`의 `build`/`test`/`lint`/`format`; `devDependencies`에서 포매터(prettier/biome)·테스트러너(jest/vitest) |
| `tsconfig.json` | TypeScript | `strict` 여부 참고 |
| `go.mod` | Go | `go build ./...`, `go test ./...`, `go vet ./...`; golangci-lint 설정 파일 있으면 `golangci-lint run` |
| `pyproject.toml` / `requirements.txt` | Python | `pytest`; ruff/black 설정 있으면 포매터로 |
| `Cargo.toml` | Rust | `cargo build`, `cargo test`, `cargo clippy`, `cargo fmt` |
| `pom.xml` / `build.gradle` | Java/Kotlin | `mvn test` 또는 `gradle test` |
| `Gemfile` | Ruby | `rspec`/`rake test`, rubocop |
| 신호 파일 없음 | 빈/미지의 프로젝트 | Step 1에서 언어를 직접 묻는다 |

여러 신호가 동시에 있으면(모노레포 등) 가장 바깥/주된 것을 기본으로 삼고, 확인 질문에 "여러 개 감지됨"을 알린다.

---

## 2. Step 0 — 기존 설정 보완 방식

기존 `.claude/` 또는 `CLAUDE.md`가 감지됐을 때만 묻는다.

- **질문:** "이미 설정이 좀 있네요. 어떻게 할까요?"
- **선택지:**
  - `보완하기 (추천)` — 기존 파일은 그대로 두고, 빠진 부분만 추가합니다
  - `처음부터` — 기존 파일을 .bak 으로 백업하고 새로 만듭니다
  - `특정 부분만` — 어떤 영역을 손댈지 다음에 고릅니다

`특정 부분만` 선택 시 후속 질문(다중 선택):
- "어디를 손댈까요?" → `CLAUDE.md` / `권한·훅` / `규칙(rules)` / `에이전트·스킬`

---

## 3. Step 2 — 깊이 선택

- **질문:** "어디까지 설정해드릴까요? 작게 시작해서 나중에 늘릴 수 있어요."
- **선택지:**
  - `기본 (추천)` — CLAUDE.md + 권한 설정. 가장 빠르게 시작
  - `표준` — 기본에 더해 규칙 파일을 주제별로 생성
  - `확장` — 표준에 더해 코드 리뷰 에이전트 등 스타터까지

`$ARGUMENTS`로 깊이가 지정되면(`빠른`/`기본`/`표준`/`확장`) 이 질문을 건너뛴다. `빠른`은 `기본` + 후속 질문 최소화(감지값을 그대로 채택, 확인만 1회).

## 5. Step 3 — 핵심 설정 질문들

### 5-1. 명령어 확인 (모든 깊이)

- **질문:** "감지한 명령어가 맞나요?" — 본문에 감지 결과를 보여준다 (예: `build: npm run build / test: npm test / lint: npm run lint`).
- **선택지:** `맞아요 (추천)` / `일부 다름` / `명령어 없음(스킵)`
- `일부 다름` 선택 시, 어떤 명령이 틀렸는지 후속으로 받아 직접 입력하게 한다.

### 5-2. 코드 컨벤션 (표준·확장만)

가볍게 2~3개만. 감지값이 있으면 기본 선택으로.

- **타입 엄격성** (TS 등): `strict 사용 (추천)` / `느슨하게` / `해당 없음`
- **export 스타일** (JS/TS): `named export (추천)` / `default export` / `상관없음`
- **테스트 파일 위치:** `소스 옆 (foo.ts → foo.test.ts) (추천)` / `별도 test 폴더` / `상관없음`

> 언어에 맞지 않는 질문은 건너뛴다. 컨벤션은 깊이 파고들지 말고 핵심만. 더 필요하면 사용자가 나중에 rules에 추가하면 된다고 안내.

### 5-3. 권한 (모든 깊이)

- **질문:** "자주 쓰는 안전한 명령은 확인 없이 실행하도록 허용하고, 위험한 명령은 막을까요?"
- **선택지:** `둘 다 (추천)` / `허용만` / `차단만` / `기본값만(아무것도 추가 안 함)`
- 자동 허용 후보 = Step 1에서 확인된 test·lint·build·format 명령. 차단 후보 = `Bash(rm -rf *)`, force push 류.

### 5-4. 자동 포맷 훅 (포매터 감지 시에만)

- **질문(한 줄 설명 포함):** "'훅'은 특정 순간에 자동 실행되는 작은 동작이에요. 파일을 편집할 때마다 포매터(`<감지된 포매터>`)를 자동으로 돌릴까요?"
- **선택지:** `네, 자동 포맷 (추천)` / `아니요`
- 포매터가 감지되지 않으면 이 질문 자체를 건너뛴다(작동 안 할 훅을 만들지 않는다).

---

## 6. Step 4 — 스타터 (확장 깊이만)

- **질문:** "맛보기용 스타터를 만들어 둘까요? 나중에 직접 늘릴 수 있어요." (다중 선택 가능)
- **선택지:**
  - `code-reviewer 에이전트` — 읽기 전용으로 코드를 검토하는 보조 에이전트
  - `스타터 스킬 (/run-checks)` — test·lint를 한 번에 돌리는 단축 스킬
  - `둘 다`
  - `아니요`
- 선택된 항목만 `references/templates.md`의 해당 템플릿으로 생성한다.

---

## 7. Step 5 — 미리보기 확인

- **질문:** "이대로 만들까요?" — 본문에 생성/수정 파일 트리와 핵심 내용 미리보기를 보여준 뒤 묻는다.
- **선택지:** `만들기 (추천)` / `일부 수정` / `취소`
- `일부 수정` 선택 시 "어디를 고칠까요?"로 해당 Step으로 돌아간다.
